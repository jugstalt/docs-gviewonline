    REST-API v2¶

    Die API v2 ist ressourcenorientiert und liegt unter /api/v2/indices. Sie läuft parallel zur API v1 (/Lucene/...): Beide arbeiten auf denselben Indizes mit derselben Engine, bestehende v1-Clients funktionieren unverändert weiter. v1 gilt als deprecated; neue Clients sollten v2 verwenden.

    Antworten, Rollen, Query-Syntax, outFields-Funktionen, Geo-Filter und format sind wie in v1. Jede Version hat ein eigenes OpenAPI-Dokument (/openapi/v1.json, /openapi/v2.json); die API-Referenz-UI (/scalar) zeigt beide.

    Fehler und HTTP-Statuscodes¶

    Anders als v1 (immer HTTP 200) liefert v2 Fehler mit passendem Statuscode. Der Body ist in beiden Fällen gleich:

    { "success": false, "message": "Cannot parse 'title:(': ..." }
    Status Ursache
    400 Ungültige Query (Lucene-Syntax), ungültiger Geo-Filter, ungültige Parameter (z. B. from + size > 10000, ungültiger Index-Name)
    404 Index existiert nicht
    409 Index existiert bereits bzw. wird gerade entladen
    413 Request-Body zu groß (LuceneServer:MaxRequestBodySizeBytes)
    500 Sonstige Fehler (Meldung außerhalb von Development nur mit Fehlertyp)

    Suche und Paging¶

    [GET] /api/v2/indices/{index}/search?q=&outFields=&from=0&size=20&searchAfter=&sortField=&sortReverse=&filter=&format=

    Parameter Beschreibung
    from Offset des ersten Treffers (Standard 0). from + size darf 10000 nicht überschreiten.
    size Seitengröße (Standard 20).
    searchAfter Cursor für die nächste Seite: Wert von nextSearchAfter aus der vorigen Antwort. Nur bei Relevanz-Sortierung (ohne sortField), nicht mit from kombinierbar. 
    {
  "hits": [ ... ],
  "totalHits": 1234,
  "from": 20,
  "size": 20,
  "nextSearchAfter": "MTIzOjEuNDI3Mjg0OA",
  "success": true,
  "milliSeconds": 2.1
}
    • totalHits ist die Gesamtzahl der Treffer, unabhängig von from/size.
    • nextSearchAfter ist null, wenn die Seite weniger als size Treffer hat oder sortField verwendet wird.
    • Offset-Paging (from) ist einfach und passt für Ergebnislisten mit Seitenzahlen. Intern werden from + size Treffer gesammelt, tiefe Seiten werden daher teuer (deshalb das Limit).
    • Cursor-Paging (searchAfter) ist effizient für tiefes Blättern bzw. Exporte. Der Cursor ist nur stabil, solange der Index zwischenzeitlich nicht verändert wird.
    • format={geo-feld}:geojson liefert GeoJSON ohne Paging-Informationen.

    Dieselben Paging-Parameter und Antwortfelder gibt es auch in v1 (/Lucene/search/{index} und /Lucene/searchphonetic/{index}).

    Aliases¶

    Ein Alias zeigt auf genau einen Index. Überall, wo eine Index-ID erwartet wird (v1 und v2: Suche, Gruppen, Dokumente, Mapping, Metadaten, Stats, Export, Refresh), kann stattdessen ein Alias verwendet werden. Anlegen und Löschen von Indizes verwendet immer den echten Indexnamen.

    # neue Generation aufbauen, dann den Alias atomar umschalten
curl -X PUT  http://localhost:8080/api/v2/indices/orte_20261107
# ... Mapping, Dokumente, Refresh ...
curl -X PUT  http://localhost:8080/api/v2/aliases/orte -H "Content-Type: application/json" -d '{"index":"orte_20261107"}'
curl         "http://localhost:8080/api/v2/indices/orte/search?q=graz"

    Regeln: Ein Alias darf nicht wie ein bestehender Index heißen (409) und muss auf einen Index zeigen, nicht auf einen anderen Alias; ein Index, auf den ein Alias zeigt, lässt sich nicht löschen (409, Alias vorher entfernen oder umschalten); DELETE /api/v2/indices/{alias} liefert 409. Gespeichert in {RootPath}/aliases.json, Kopie in {ArchivePath}/aliases.json.
