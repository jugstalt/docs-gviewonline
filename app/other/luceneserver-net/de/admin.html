    Admin-Oberfläche¶

    LuceneServerNET.Admin ist eine eigene Webanwendung (Blazor Server, MudBlazor), mit der eine oder mehrere LuceneServer.NET-Instanzen administriert werden. Sie spricht die Server ausschließlich über die REST-API v2 an und kann daher überall laufen, wo die Server erreichbar sind.

    Funktionen¶

    Bereich Möglichkeiten
    Dashboard Health, Version, Uptime, Speicher und Anzahl der Indizes jeder Instanz, Rollen des API-Clients
    Instanzen Instanzen anlegen, bearbeiten, entfernen und testen (zusätzlich zu denen aus der Konfiguration)
    Indizes Liste mit Dokumentanzahl, Größe auf der Platte und letzter Änderung; filtern und sortieren
    Suche Autocomplete-Eingabe (Search as you type, jedes Wort ist ein Pflicht-Präfix: graz haupt → +graz* +haupt*), Suche mit size/from/searchAfter, Sortierung, räumlicher Filter, phonetische Suche, Gruppierung, Ergebnis als Tabelle oder JSON, Request als curl-Befehl
    Index anlegen Mapping-Editor: Felder, Typen, indiziert/gespeichert, Primärfelder, Phonetik
    Datenbank-Verbindungen SQL Server-, PostgreSQL- und SQLite-Verbindungen als Importquelle (verschlüsselt gespeichert), Verbindungstest (auch in der Liste); Show connection string zeigt den gespeicherten String mit maskiertem Passwort (Audit-Log connection.show), ein belassenes ***** behält das gespeicherte Passwort
    Import Aus einer Datenbank-Abfrage oder CSV, JSON bzw. GeoJSON (inkl. Geodaten) (Array oder NDJSON) hochladen, Vorschau, Mapping aus den ersten 200 Zeilen vorgeschlagen (neuer Index) bzw. Spalten dem bestehenden Mapping zugeordnet, einstellbare Batchgröße, Abbruch, Fehlerreport
    Metadaten Eigene Metadaten anzeigen und bearbeiten
    Import-Jobs Wiederkehrende Importe aus einer Datenbank-Abfrage (Cron-Zeitplan): neu aufbauen und Alias umschalten, leeren und neu befüllen oder anhängen; Lauf-Verlauf
    Audit-Log Wer wann was geändert hat (Index, Metadaten, Import, Instanzen, Verbindungen, Logins), mit Filtern; Aufbewahrung Admin:Audit:RetentionDays (Standard 180)
    Aliases Index-Aliases anlegen, umschalten und entfernen (siehe API v2); Aliases stehen in der Indexliste; ein Klick auf einen Alias öffnet seine Seite: Suche, curl-Befehl, Kopieren und Backup verwenden den Alias-Namen (immer die aktuelle Generation); Wartung und Import nur direkt am Index
    Backup / Restore Index als ZIP herunterladen (Backup auf der Index-Seite) und auf einer beliebigen Instanz wiederherstellen (Restore in der Indexliste)
    Kopieren Index (Mapping, Metadaten, Dokumente) unter neuem Namen auf derselben oder auf eine andere Instanz kopieren
    Wartung Refresh, Dokumente per Query löschen, Index leeren, Index löschen (Rolle admin, Bestätigung per Name)

    Die Oberfläche bietet nur an, was der API-Client der Instanz darf: Sie fragt den Server (GET /api/v2/admin/whoami) nach den Rollen read, write und admin.

    Starten¶

    Der AppHost startet Server und Admin-Oberfläche:

    dotnet run --project src/aspire/LuceneServerNET.AppHost

    Login admin / admin (Parameter admin-password, in den User Secrets des AppHost änderbar).

    dotnet run --project src/LuceneServerNET.Admin

    ./build.cmd DockerBuild   # oder: docker pull ghcr.io/jugstalt/luceneserver-net-admin
docker run --rm ghcr.io/jugstalt/luceneserver-net-admin --hash-password "mein passwort"
docker run -p 8081:8080 -v luceneserver-admin-data:/data \
  -e Admin__Authentication__Users__0__Name=admin \
  -e Admin__Authentication__Users__0__PasswordHash='pbkdf2-sha256$...' \
  -e Admin__Instances__0__Name=prod \
  -e Admin__Instances__0__Url=http://luceneserver:8080 \
  ghcr.io/jugstalt/luceneserver-net-admin

    Als Windows-Dienst betreiben¶

    Das Release-ZIP (luceneserver-net-win64-{version}.zip) enthält die Admin-Oberfläche in {version}/admin und zwei Skripte im Versionsordner:

    Skript Zweck
    lucene-admin.bat startet die Admin-Oberfläche in einer Konsole (http://localhost:5180)
    lucene-admin-service.bat installiert sie als Windows-Dienst

    Import-Jobs laufen nur, solange die Anwendung läuft. Ein Windows-Dienst startet mit dem Server und wird nach einem Absturz neu gestartet; unter Windows ist das daher der empfohlene Weg. Das Skript in einer Eingabeaufforderung als Administrator ausführen:

    lucene-admin-service.bat install [name] [port]
lucene-admin-service.bat uninstall [name]

    install legt den Dienst an und startet ihn:

    • Dienstname lucene-admin, mit Namen lucene-admin-<name>. Er startet automatisch (verzögert) und wird nach einem Absturz neu gestartet.
    • Er hört auf http://localhost:<port> (Standard 5180). Für den Zugriff von anderen Rechnern einen Reverse Proxy (IIS mit ARR, nginx, ...) mit HTTPS davorsetzen.
    • Er läuft unter dem virtuellen Konto NT SERVICE\lucene-admin[-<name>], das nur in admin-data schreiben und _config lesen darf.
    • Neben den Versionsordnern (überleben Updates): admin-data (SQLite-Datenbank admin.db, Data-Protection-Schlüssel) und _config\admin.json. Bei der ersten Installation legt das Skript admin.json mit leerer Benutzerliste an: einen Benutzer (admin\LuceneServerNET.Admin.exe --hash-password <passwort>) und Instanzen eintragen, dann den Dienst neu starten. admin.json überschreibt appsettings.json; Umgebungsvariablen überschreiben admin.json.
    D:\lucene-admin\
  3.0.0\                          Versionsordner aus dem ZIP
    admin\                        Anwendung
    lucene-admin-service.bat
  admin-data\                     admin.db, keys
  _config\admin.json              Konfiguration

    Mehrere Instanzen auf einem Server: ein Stammordner pro Instanz, jeweils mit eigenem Namen und Port. install verweigert einen Namen, dessen Dienst zu einem anderen Stammordner gehört.

    Update: die neue Version in denselben Stammordner entpacken und ihr lucene-admin-service.bat install mit gleichem Namen und Port ausführen. Das Skript stoppt den Dienst, stellt ihn auf die neue Version um und startet ihn wieder (Datenbank-Migrationen laufen beim Start). Zurück geht es mit install der alten Version (nur, wenn die neue Version die Datenbank nicht migriert hat).

    Eigenes Konto: für SQL Server mit Windows-Authentifizierung braucht das virtuelle Konto einen Login am SQL Server (NT SERVICE\lucene-admin), oder in den Diensteigenschaften (Reiter Anmelden) ein Domänenkonto eintragen und ihm dieselben Rechte geben.

    Warnungen und Fehler gehen ins Windows-Ereignisprotokoll (Anwendungsprotokoll, Quelle LuceneServer.NET Admin).

    IIS¶

    Die Admin-Oberfläche läuft auch im IIS (ASP.NET Core Hosting Bundle, In-Process). IIS startet die Anwendung erst mit der ersten Anfrage und recycelt sie (Leerlauf-Timeout, standardmäßig alle 29 Stunden); geplante Import-Jobs laufen im IIS daher nicht verlässlich. Entweder:

    • die Oberfläche im IIS mit Admin:Jobs:Enabled = false betreiben und zusätzlich den Windows-Dienst auf demselben DataPath (er führt die Jobs aus; gleiche Data-Protection-Schlüssel, beide können die gespeicherten Secrets entschlüsseln), oder
    • den Anwendungspool einstellen: Startmodus AlwaysRunning, Leerlauf-Timeout 0, kein periodisches Recycling, und Vorabladen aktiviert true an der Site (Feature Anwendungsinitialisierung). Verpasste Läufe werden nach einem Recycle nachgeholt (Catch up missed runs).

    Die Identität des Anwendungspools braucht Schreibrechte auf DataPath. Blazor Server braucht WebSockets (IIS-Feature WebSocket-Protokoll).

    Konfiguration¶

    {
  "Admin": {
    "DataPath": "_data",            // SQLite-Datenbank (admin.db) + Data-Protection-Schlüssel
    "PublicUrl": "https://admin.example.com",  // optional: Links in Job-Webhooks
    "Import": { "MaxFileSizeMB": 500, "CommandTimeoutSeconds": 600 },
    "Audit": { "RetentionDays": 180 },
    "Jobs": { "Enabled": true },    // false: keine geplanten Läufe (z. B. eine zweite Admin-Instanz auf derselben Datenbank)
    "Authentication": {
      "Type": "Local",              // Local | Oidc | None (None: kein Login, nur lokale Entwicklung!)
      "Users": [
        { "Name": "admin", "PasswordHash": "pbkdf2-sha256$..." }
      ],
      "Oidc": {
        "Authority": "https://login.example.com/realms/main",
        "ClientId": "lucene-admin",
        "ClientSecret": "...",
        "Scopes": [ "openid", "profile" ],
        "RequiredRole": "lucene-admin"   // optional, Rollen-Claim "roles"
      }
    },
    "Instances": [
      { "Name": "prod", "Url": "https://lucene.example.com", "ClientId": "admin-ui", "ClientSecret": "..." }
    ]
  }
}
    • Passwort-Hashes: LuceneServerNET.Admin --hash-password <passwort> (gleiches Format wie --hash-secret des Servers). Ein Klartext-Password funktioniert ebenfalls, erzeugt aber eine Warnung im Log.
    • Konfigurationsdatei außerhalb des Anwendungsordners: die Umgebungsvariable LUCENE_ADMIN_CONFIG=<pfad>dmin.json lädt eine zusätzliche Datei, die appsettings.json überschreibt (verwenden die Windows-Dienst-Skripte).
    • Instanzen aus der Konfiguration sind in der Oberfläche schreibgeschützt. In der Oberfläche angelegte Instanzen liegen in admin.db; ihre Client-Secrets werden mit ASP.NET Core Data Protection verschlüsselt (Schlüssel in DataPath/keys). DataPath muss auf einem persistenten Volume liegen, sonst lassen sich gespeicherte Secrets nach einem Neustart nicht mehr entschlüsseln.
    • API-Client pro Instanz: Am Server einen Client anlegen (siehe Authentifizierung), mit der Rolle, die in der Oberfläche erlaubt sein soll, z. B. admin für volle Administration oder read nur für die Suche.

    Warning

    Wer sich an der Admin-Oberfläche anmelden kann, darf auf allen Instanzen alles, was die konfigurierten API-Clients dürfen. Nicht ohne OIDC oder starke Passwörter öffentlich erreichbar machen und HTTPS verwenden.

    Import¶

    1. Bestehenden Index auswählen oder den Namen eines neuen Index eingeben.
    2. Datei: CSV-Datei (Kopfzeile, Trennzeichen , ; Tab oder | wird erkannt) oder JSON (Array von Objekten, { "items": [...] } oder NDJSON) hochladen. Datenbank: Verbindung wählen (Menü Database connections), SELECT-Abfrage eingeben und Preview klicken. Der Indexname wird aus der Tabelle nach FROM übernommen.
    3. Vorgeschlagenes Mapping prüfen. Regeln: Ganzzahlen → int32, Zahlen → double, ISO-Datum → datetime, kurze Werte ohne Leerzeichen → string, alles andere → text. Spalten lat/lon (auch latitude/longitude, lng) werden zusätzlich zu einem geo-Feld location kombiniert. Textfelder werden Primärfelder. Feldnamen dürfen nicht mit _ beginnen.
    4. Batchgröße wählen (Dokumente pro Request, Standard 500) und starten. Zeilen, die nicht zum Mapping passen, werden übersprungen und im Report aufgelistet; lehnt der Server einen Batch ab, werden dessen Dokumente einzeln gesendet, um die fehlerhaften Zeilen zu finden. Am Ende wird der Index einmal refresht.

    Import aus einer Datenbank¶

    • Provider: SQL Server (Microsoft.Data.SqlClient), PostgreSQL (Npgsql), SQLite (Microsoft.Data.Sqlite).
    • Erlaubt ist nur eine einzelne SELECT-Anweisung (oder WITH ... SELECT). Sie läuft in einer Transaktion, die immer zurückgerollt wird. Das ist ein Sicherheitsnetz, kein Berechtigungskonzept: einen Datenbank-User mit reinen Leserechten verwenden.
    • Die Abfrage läuft zweimal: für die Vorschau (erste 200 Zeilen) und für den Import (gestreamt, alle Zeilen). Gleichnamige Spalten bekommen ein Suffix (id, id2), Binärspalten werden übersprungen, decimal wird zu double.
    • Timeout pro Abfrage: Admin:Import:CommandTimeoutSeconds (Standard 600).

    Geodaten¶

    Quelle Erkannt als
    Spalten lat/lon (auch latitude/longitude, lng) Punkt, EPSG:4326
    Spalten x/y (auch rechtswert/hochwert, easting/northing) Punkt, der EPSG-Code muss gewählt werden
    Geometrie-Spalte: WKB/EWKB (Bytes), WKT/EWKT (SRID=31256;POLYGON(...)), GeoJSON-Geometrie Punkt, Linie, Polygon (auch Multi)
    GeoJSON-Datei (.geojson, FeatureCollection) properties werden Felder, geometry eine Geometrie-Spalte, id das Feld id

    Weitere Koordinatenspalten lassen sich im Mapping hinzufügen (Add point from columns).

    • Koordinatensystem: Eine SRID im Wert (EWKB, EWKT, GeoJSON crs) hat Vorrang, sonst gilt der EPSG-Code des Geo-Felds (Standard 4326). Alles wird mit Proj4Net.Core nach WGS84 umgerechnet; unbekannte EPSG-Codes werden vor dem Import gemeldet.
    • Linien und Polygone: Der Server indiziert Punkte, das geo-Feld bekommt daher den Point on Surface (liegt immer auf der Linie bzw. im Polygon, berechnet mit SpatialNET im Quellsystem). Die Bounding-Box steht in <feld>_bbox als "minx,miny,maxx,maxy" (WGS84, nicht indiziert); Punkte bekommen keine.
    • Template-Felder (Add template field): ein Feld aus mehreren Spalten, z. B. {PLZ} {ORT} {STR} {HNR} oder Adresse in {ORT} ({ORTSTEIL}). Spaltennamen ohne Groß-/Kleinschreibung, NULL ist leer, Zahlen kulturunabhängig (12.5), Datum ISO; mehrfache Leerzeichen werden zusammengefasst und leere Klammern () / [] entfernt. Replacements (von → nach) gelten für alle Template-Felder.
    • Original-Geometrie (optional, standardmäßig aus): <feld>_geojson, GeoJSON in WGS84 mit 7 Nachkommastellen (RFC 7946).
    • Datenbanken: PostGIS-Spalten geometry / geography werden direkt gelesen (als EWKB mit SRID, auch bei SELECT *). SQL-Server-Geometrietypen als WKB abfragen:
    -- PostGIS: direkt, oder ausdrücklich als EWKB (behält die SRID)
SELECT id, name, geom FROM places
SELECT id, name, ST_AsEWKB(geom) AS geom FROM places
-- SQL Server geometry / geography (EPSG-Code im Mapping wählen)
SELECT id, name, geom.STAsBinary() AS geom FROM places

    Gesucht wird mit dem räumlichen Filter auf das Geo-Feld, z. B. dist_km(geom:15.44,47.07,5) oder bbox(geom:15.4,47.0,15.5,47.1).

    Kopieren¶

    Copy auf der Index-Seite kopiert Mapping, Metadaten und alle Dokumente unter einen neuen Indexnamen oder auf eine andere Instanz (der API-Client des Ziels braucht die Rolle write). Die Dokumente kommen aus GET /api/v2/indices/{id}/documents/_export, der nur gespeicherte Felder liefert: Felder mit "store": false gehen beim Kopieren verloren (die Seite zeigt sie vorher an). Ein bestehendes Ziel wird nur mit Replace the target if it exists überschrieben.

    Import-Jobs¶

    Import jobs führen Datenbank-Abfragen (eine oder mehrere Quellen) nach Zeitplan, manuell oder von außen ausgelöst aus und importieren das Ergebnis. Das Mapping wird einmal über die Vorschau erkannt, kann angepasst werden und wird mit dem Job gespeichert (die Spalten der Abfragen dürfen sich danach nicht ändern).

    Modus Ablauf
    Neu aufbauen und Alias umschalten Ein neuer Index {alias}_{yyyyMMddHHmmss} wird angelegt (ohne Archiv, er wird bei jedem Lauf neu aufgebaut) und befüllt; bei Erfolg wird der Alias umgeschaltet und ältere Generationen werden gelöscht, bis auf die neuesten Keep older generations (Standard 1, für ein Rollback über die Alias-Seite). Generationen, auf die irgendein Alias zeigt, werden nie gelöscht. Schlägt der Lauf fehl, wird die neue Generation entfernt und der Alias bleibt unverändert. Clients verwenden den Alias-Namen.
    Leeren und neu befüllen Der Index wird geleert und neu befüllt (Suchen sehen währenddessen einen leeren bzw. halben Index).
    Anhängen Dokumente werden hinzugefügt.
    • Zeitplan: Cron-Ausdruck mit 5 Feldern (Minute Stunde Tag Monat Wochentag, z. B. 0 3 * * *) und Zeitzone (leer = UTC). Die Seite zeigt die nächsten Läufe. Ohne Cron-Ausdruck (manual) läuft der Job nur über Run now.
    • Fortschritt eines laufenden Jobs (Job-Liste und Job-Seite): gelesene Zeilen, Rate und Laufzeit; ab dem zweiten Lauf ein Prozentwert, geschätzt aus der Zeilenzahl des letzten erfolgreichen Laufs.
    • Dry run (Job-Seite): liest und konvertiert alle Zeilen wie ein Lauf, schickt aber nichts (kein Index, keine Metadaten, kein Alias). Jeder Lauf zeigt, wo die Zeit bleibt: read (Datenbank), convert (Templates, Geometrie) und send (Server).
    • Jetzt ausführen, Abbrechen und ein Lauf-Verlauf (Status, Dauer, Zahlen, Index, Meldung) pro Job. Jeder Lauf steht im Audit-Log.
    • Externer Auslöser: den Job von außen starten statt (oder zusätzlich zu) einem Zeitplan, z. B. am Ende eines Jenkins-Jobs, der die Datenbank aktualisiert. Siehe Import-Jobs von außen auslösen.
    • Webhook (optional): nach einem Lauf wird die URL mit POST und einem JSON-Body aufgerufen, entweder nur bei Fehlern (failed, cancelled, interrupted; Standard) oder nach jedem Lauf. Ein optionaler Header Name: Wert (z. B. Authorization: Bearer ...) wird verschlüsselt gespeichert. Bis zu 3 Versuche (5 s Abstand, 30 s Timeout); das Ergebnis steht im Lauf-Verlauf, ein fehlschlagender Webhook ändert den Status des Laufs nicht. Test webhook schickt ein Beispiel. Das Feld text ist eine einzeilige Zusammenfassung, die Slack- und Mattermost-Incoming-Webhooks direkt anzeigen:
    {
  "text": "❌ Import job orte: failed · prod/orte_20261107030000 · read 10, imported 9, failed 1 · 12.5 s · ...",
  "job": "orte", "jobId": 7, "runId": 3, "instance": "prod", "target": "orte", "mode": "replace_alias",
  "index": "orte_20261107030000", "status": "failed", "success": false, "triggeredBy": "job:orte",
  "startedUtc": "2026-11-07T03:00:00Z", "finishedUtc": "2026-11-07T03:00:12.5Z", "durationSeconds": 12.5,
  "read": 10, "imported": 9, "failed": 1, "message": "...", "url": "https://admin.example.com/jobs/7"
}

    status ist succeeded, warning (Zeilen übersprungen), failed, cancelled oder interrupted; url gibt es nur, wenn Admin:PublicUrl konfiguriert ist. - Läufe finden nur statt, solange die Admin-App läuft. Mit Catch up missed runs (Standard an) läuft ein Job beim Start einmal, wenn ein geplanter Lauf verpasst wurde, während die App nicht lief (nur einmal, egal wie viele verpasst wurden). Läufe, die bei einem Herunterfahren aktiv waren, werden als interrupted markiert. Für verlässliche Zeitpläne die Admin-App als Dienst betreiben (siehe Als Windows-Dienst betreiben). Pro Datenbank nur eine Admin-Instanz mit Admin:Jobs:Enabled = true betreiben.

    Quellen und die webgis-Vorlage¶

    Ein Job hat eine oder mehrere Quellen (Reiter auf der Job-Seite): jeweils mit eigener Datenbank-Verbindung, Abfrage, Mapping und Metadaten. Alle Quellen werden in denselben Index (dieselbe Generation) importiert; bei Neu aufbauen und Alias umschalten wird der Alias nach der letzten Quelle umgeschaltet. Ein Feld, das mehrere Quellen verwenden, muss überall denselben Typ haben. Phonetik und Encode characters gelten für den Index.

    Metadaten pro Quelle: im Index unter der Meta-ID der Quelle gespeichert (32 Hex-Zeichen, einmal erzeugt, für jeden Lauf gleich) als JSON {"id", "category", "sample", "description", "service", "query", ...} plus eigene Schlüssel. Im Modus Leeren und neu befüllen werden Einträge von Quellen, die aus dem Job entfernt wurden (Schlüssel im Format einer Meta-ID), gelöscht.

    Template-Variablen: {@metaid} (Meta-ID der Quelle) und {@category} (Kategorie aus den Metadaten).

    webgis-Vorlage (Apply webgis template nach der Vorschau, ID-Spalte wählen): die Struktur des webgis-Suchindex, die das gView-Werkzeug FillLuceneServer ablöst:

    Feld Inhalt
    id {@metaid}.{ID-Spalte} – webgis liest daraus die Meta-ID, aus den Metadaten Service und Query und das Objekt über seine ID
    suggested_text Template, z. B. {PLZ} {ORT} {STR} {HNR} (Primärfeld, Pflicht)
    subtext Template, z. B. Adresse in {ORT} ({ORTSTEIL}) (Primärfeld)
    category {@category} (Primärfeld; die Kategorie in den Metadaten ist Pflicht)
    thumbnail_url Template oder feste URL (nur gespeichert)
    geo, bbox die erste Geo-Quelle (Punkt; Linien und Polygone: Punkt auf der Fläche, bbox in WGS84)

    Die übrigen Spalten bleiben im Mapping sichtbar, werden aber nicht importiert. Die ID-Spalte wird vorgeschlagen (objectid, oid, fid, gid, id, sonst die erste Ganzzahl-Spalte). Die Meta-ID bleibt bei jedem Lauf gleich, die Dokument-IDs sind also stabil (gView hat bei jedem Befüllen eine neue erzeugt).

    gView-Konfiguration: Import gView configuration auf der Job-Seite legt aus einem gView-FillLuceneServer-JSON einen Job an (eine webgis-Quelle pro Feature-Klasse, SELECT * FROM {name} WHERE {filter}, Templates, Kategorie, Ersetzungen, Metadaten, Phonetik, Encode-Zeichen). Die Connection-Strings der Datei werden nicht verwendet: eine Datenbank-Verbindung wählen.

    Import-Jobs von außen auslösen¶

    Create trigger token auf der Job-Seite erzeugt ein Token für diesen Job. Es wird nur einmal angezeigt (gespeichert als SHA-256-Hash), darf nur diesen Job starten und kann erneuert oder widerrufen werden. Jeder Aufruf steht im Audit-Log (job.trigger, mit IP-Adresse).

    # Jenkins (sh), am Ende des Jobs, der die Datenbank aktualisiert
curl --fail -X POST "https://admin.example.com/api/jobs/7/run" \
     -H "Authorization: Bearer $LUCENE_JOB_TOKEN" \
     -H "Content-Type: application/json" -d "{\"note\":\"jenkins #$BUILD_NUMBER\"}"

    rem Jenkins (bat)
curl --fail -X POST "https://admin.example.com/api/jobs/7/run" -H "Authorization: Bearer %LUCENE_JOB_TOKEN%" -H "Content-Type: application/json" -d "{\"note\":\"jenkins #%BUILD_NUMBER%\"}"

    Das Token in einem Jenkins-Credential (Secret text) ablegen, nicht in der Job-Definition.

    Aufruf Antwort
    POST /api/jobs/{id}/run 202 {"status":"started","runId":12,"statusUrl":"/api/jobs/7/runs/12"}; läuft der Job gerade: 202 {"status":"queued"} – er läuft direkt nach dem aktuellen Lauf noch einmal (mehrere Aufrufe während eines Laufs: ein weiterer Lauf)
    GET /api/jobs/{id}/runs/{runId} 200 mit status, finished, success, Zeiten, Zahlen, message, note, webhook
    Job oder Token ungültig 401
    Job deaktiviert 409
    • Das Token geht als Authorization: Bearer <token> mit (oder im Header X-Job-Token). Die optionale note (JSON-Body oder ?note=, max. 200 Zeichen) steht im Lauf-Verlauf und wird mit dem Webhook geschickt.
    • Der Aufruf kehrt sofort zurück. Soll der Jenkins-Build bei einem fehlgeschlagenen Import fehlschlagen, die statusUrl abfragen, bis finished true ist, und success prüfen; für Benachrichtigungen reicht meist der Webhook des Jobs.
    • Ein Zeitplan kann als Sicherheitsnetz bleiben (z. B. 0 6 * * *): er läuft unabhängig vom Auslöser.
    • Die Admin-Oberfläche muss von Jenkins aus erreichbar sein (HTTPS, siehe Als Windows-Dienst betreiben / IIS).

    Backup und Restore¶

    Backup auf der Index-Seite lädt ein ZIP herunter:

    Datei Inhalt
    manifest.json Format, Index, Instanz, Server-Version, Zeitpunkt, Anzahl Dokumente, nicht gespeicherte Felder
    mapping.json das Mapping
    metadata.json die eigenen Metadaten
    documents.ndjson alle Dokumente (gespeicherte Felder, ein JSON-Objekt pro Zeile)

    Restore in der Indexliste lädt so ein ZIP hoch (max.
